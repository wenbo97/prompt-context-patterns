> Independent teaching constructions, not observed model outputs or measured performance.

## Use case

A worker reconnects after a network gap. A history request may include events emitted during the gap while a newly opened live stream is already buffering newer events.

## Mechanism

Open the live stream first, fetch and process available history, then consume the live tail. Gate event side effects on unseen IDs, but evaluate terminal or idle-stop conditions for every live event, including duplicates.

## Bad example

```text
Reconnect from now and assume the stream replays the gap, or skip a repeated event with continue before checking whether it marks the session terminal.
```

## Good example

```text
Open the replacement stream, read history and record its IDs, then tail the stream. Ignore duplicate handling while still applying the lifecycle stop check to a repeated terminal event.
```

## Why the change matters

History covers the disconnect interval while the live stream covers events after reconnection; overlap can repeat events. Separate deduplication from lifecycle checks to avoid duplicate side effects without suppressing termination.

## Observable expectation

For history and stream data actually returned, each stable event ID is handled at most once and an observed terminal event can still stop the consumer.

## Limits

Confirm history pagination/completeness, retention, ordering, stable IDs and stop semantics for the target API/SDK. This cannot recover events absent from history or establish a delivery guarantee; preserve order if the consumer depends on it.
