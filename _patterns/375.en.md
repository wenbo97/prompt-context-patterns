> Independent teaching constructions, not observed model outputs or measured performance.

## Use case

A partially installed toolkit has its source-reader but lacks the changed-file tracker module.

## Mechanism

Defer the optional import to its tool or contain startup failure in that subsystem. Keep unrelated registration alive, name the unavailable capability, contain diagnostic failures and permit a verified retry after repair.

## Bad example

```text
Import the tracker at the top of the shared tool barrel. A missing tracker prevents every tool from loading; alternatively catch it and return an empty changed-file list as if tracking worked.
```

## Good example

```text
Register the independent reader. Load the tracker inside changed-files or its isolated initialization boundary. If missing, return tracker-unavailable with repair guidance, not no-changes. Catch diagnostic logging failures too; invalidate a failed import promise so a repaired dependency can be retried.
```

## Why the change matters

The failure is confined before an unrelated tool is taken down, and absence remains different from a valid empty result.

## Observable expectation

With the tracker removed in a controlled fixture, reader startup remains usable while changed-files reports unavailable; after repair, a new load can succeed.

## Limits

Only optional capabilities may degrade this way; required security/checker dependencies must fail according to their own policy. Registration is not proof of usability. The actual loader and host behavior still need runtime tests.
