> Independent teaching constructions, not observed model outputs or measured performance.

## Use case

Split a feature into parser changes and UI changes.

## Mechanism

Reviewable behavior supplies a boundary more useful than raw line counts.

## Bad example

```text
Create one task per line, or one task for the entire product.
```

## Good example

```text
Parser task owns its input contract, parsing behavior and tests. UI task consumes that contract and owns interaction tests. Each has one acceptance verdict; keep coupled signature changes together rather than splitting them across uncoordinated tasks.
```

## Why the change matters

Reviewable behavior supplies a boundary more useful than raw line counts.

## Observable expectation

A reviewer can accept or reject each task using its own criteria.

## Limits

Large cross-cutting changes may need integration tasks; task size is a judgment, not a universal file limit.
