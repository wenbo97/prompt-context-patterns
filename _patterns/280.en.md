## Use case

An invoice assistant can use a shell, but sending an invoice requires a recipient-specific approval check.

## Mechanism

Define a send-invoice operation with typed recipient and invoice identity; let the harness validate scope and perform its approval and audit checks before executing the effect.

## Bad example

```text
Hide invoice sending in a shell string that the harness classifies only as generic command execution.
```

## Good example

```text
Call the typed send-invoice tool; the harness shows the exact recipient and invoice and applies its documented approval rule.
```

## Why the change matters

The harness can reason about a declared action and its arguments without inferring intent from arbitrary command text.

## Observable expectation

The action schema, approval check and executed effect can be inspected.

## Limits

A typed tool is not authorization by itself. A shell-aware harness may also enforce effects; the source claim that bash cannot enforce invariants is too broad. This differs from portable host-adapter capability verbs.
