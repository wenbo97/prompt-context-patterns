> Independent teaching constructions, not observed model outputs or measured performance.

## Use case

A tool returns a bounded slice of 2,000 records, or a response budget interrupts a twelve-section deliverable.

## Mechanism

For API records, pass through the service-issued cursor unchanged and report returned count, known total/remaining count, and truncated/completion state truthfully. For generated output, stop after a complete unit and state the actual completed count, known total or unknown total, and the next unit label; resume there without repeating prior units. These are distinct contracts: an authored unit pointer is not an API token.

## Bad example

```text
Label the first 20 API records as complete, invent a total or cursor, or stop at 6/12 generated sections while claiming completion.
```

## Good example

```text
API: return 20; state total=2,000 and remaining=1,980 only when authoritative, set truncated=true, and pass through the service-returned opaque cursor (for example C20) unchanged. Generated output: finish section six intact, state 6/12 and next_unit=section seven, then resume at seven without replay.
```

## Why the change matters

The consumer can tell partial work from complete work and continue from the correct boundary without mistaking one cursor type for another.

## Observable expectation

Every response reports only supported counts and an explicit partial/completion state; its API continuation token or generated next-unit pointer resumes the right work.

## Limits

Never fabricate totals or tokens, claim partial output complete, or use a self-authored unit label as a service cursor. Exact totals may require aggregation; unknown totals must remain unknown.
