> 以下示例与示意结果由本站编写，用于说明方法，不是模型实测结果。

## 使用场景

你要把 issue 分到错误复现、功能规划或澄清。教学 A 描述可观察失败，B 请求新行为，C 只有“改进体验”；分诊完成还需要对应证据或范围记录，不只是选一个状态名。

## 具体做法

先定义互斥条件、未匹配/冲突分支、重入条件和结束证据，再用小型 DOT 图表达。每次沿满足的边进入流程；含糊请求停在澄清，收到真实答案才回到选择。图旁说明节点完成是什么意思，避免箭头只是装饰。

## 反例

```text
适当分诊 A/B/C，不明确就问。无论有没有回答都直接标完成，也不记录选择依据。
```
{: .example--bad}

## 改进写法

```text
按教学 DOT 流程分诊：
digraph triage {
  done [shape=doublecircle];
  start -> reproduce [label=observed_failure];
  start -> plan [label=new_behavior];
  start -> clarify [label=ambiguous_or_conflicting];
  clarify -> start [label=actual_answer_received];
  reproduce -> done [label=evidence_recorded];
  plan -> done [label=scope_recorded];
}
A/B 分别进入复现/规划；C 留在 clarify，未回答不重入。复现记录或规划范围具备才到 done，这只是分诊完成，不代表功能实现完成。
```
{: .example--good}

## 为什么这样改

具名边条件让执行者和审阅者能核对为何转移，等待与重入也有明确规则。终态证据防止把选择流程、结束分诊和完成开发混为一谈。

## 如何验证

教学测试 A→reproduce、B→plan、C→clarify；C 回答为具体新行为后回到 start→plan。没有真实回答应仍在 clarify，没有范围记录也不能到 done。

检查边条件、歧义策略和终态含义；DOT 可解析不证明实际分诊遵守它。

## 适用边界

小图适合可明确分类的流程，复杂例外可以另给说明而非塞满图。DOT 描述不提供执行引擎、授权或天然互斥条件；教学的分支标签不是上游固定命令。
