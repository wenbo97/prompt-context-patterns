> These examples and illustrative results are independently authored teaching materials, not measured model results.

## Use case

Final review finds three related null defects in one parser, interacting through shared logic. Each has trigger/location/check. One owned wave avoids competing edits by one fixer per finding.

## Mechanism

Assign the full list, fixed base, allowed scope and per-item checks to one owner. Compare shared causes/distinct obligations, modify coherently and run combined coverage. Map every issue to change/result. Re-review the fix wave plus new breakage, keeping outside observations separate rather than expanding indefinitely.

## Bad example

```text
Three fixers edit the same file concurrently, each reporting one pass without integrated behavior or complete-list checks.
```
{: .example--bad}

## Good example

```text
One teaching owner reads all three issues/base. Preserve distinct triggers/checks, coordinate logic, validate together and map changes/results/open items. Review the final fix diff against originals/new breakage, not one pass as whole-wave success. Separate genuinely independent ownership without competing writes.
```
{: .example--good}

## Why the change matters

One owner sees interactions, while the complete list preserves independent obligations. Combined validation/scoped review retain integration evidence and bound churn.

## Observable expectation

An illustrative report accounts for all three and combined behavior. Missing the third trigger or overwriting another fix fails despite one owner.

Re-review follows the actual wave diff/evidence.

## Limits

Batch by interaction/ownership, not unrelated risk. Source fixed final-wave counts are workflow choices and cannot silently erase unresolved defects.
