> These examples and illustrative results are independently authored teaching materials, not measured model results.

## Use case

A coding agent claims the counter race is fixed. The teaching environment allows counter.ts changes but not test expectations. Final state/behavior, not a polished summary, establishes the result.

## Mechanism

Start isolated fixtures with allowed scope and hidden predicates. Inspect final files, complete diff, prohibited changes and behavioral checks. Use traces separately for explicit process requirements such as approval before deletion. Apply no-op detection in context: required repair with no change and persistent failure fails, but diagnosis or already-correct states do not automatically require mutation.

## Bad example

```text
Grade passed because the summary says repaired/tests green, without inspecting code. Let the agent change expected counts to match faulty behavior.
```
{: .example--bad}

## Good example

```text
Test two callers yielding 2 in the final checkout, checking only permitted implementation changed and hidden expectations untouched. No mutation with persistent fault fails repair. Grade explicit process constraints from traces and readability/taste separately.
```
{: .example--good}

## Why the change matters

An action task’s environment is its answer. End-state and scope checks expose no execution, prohibited edits or weakened standards; traces answer separate process questions.

## Observable expectation

Teaching output 1 fails despite a claimed 2. Correct 2 with deleted tests/prohibited edits still fails. Equivalent valid implementations need no fixed tool sequence. Retain final identity and assertion results; this is a check design.

## Limits

Predicates cover only declared invariants and hidden tests can be incomplete. Permission and occurrence of effects need separate checks; visual quality requires rendering/judgment. Isolation does not prove production outcomes, and unchanged files do not fail every task.
