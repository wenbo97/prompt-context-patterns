> 以下示例与示意结果由本站编写，用于说明方法，不是模型实测结果。

## 使用场景

你审查一个目录修订，不能只说页面看起来更好。教学范围含 ID 1、2、3：每个须有一个处置，active 须双语完整，merged 须有效目标，removed 须原因；还需要逐项确认内容义务，不只是字段存在。

## 具体做法

建立完整输入清单，再为每项定义可检查且足够覆盖的完成条件。把结构校验和语义评阅分开记账，逐条将来源问题与必要补救映射到保留内容。每项处置、覆盖和完成主张分别检查，缺失项保持可见；某一检查通过不能跳过其他要求。

## 反例

```text
博客看起来改善，示例数量增加就完成。仅统计三个 ID 都在文件里，即使缺双语或漏掉审阅义务也不再核对。
```
{: .example--bad}

## 改进写法

```text
对教学 ID 1/2/3 逐项核对：每项一个 active/merged/removed 决定；active 具备双语任务、做法、对照、检查和边界；merged 目标存在；removed 原因明确。运行引用与覆盖校验，并逐条人工确认来源义务及补救有保留内容，不只比数量或关键词。报告结构结果、语义覆盖和未决项分别如何满足；缺一项仍未完成。
```
{: .example--good}

## 为什么这样改

可检查的条件阻止模糊结束，完整清单防止只挑已经做好的部分。语义映射再说明保留文本是否真能解决原义务，避免计数一致却要求遗漏。

## 如何验证

教学删除 ID 2 的原因或一份 active 英文正文，应检出缺失；补回字段但内容仍漏掉必要失败处理，结构可能通过而语义仍不通过。

最终只有每项要求有实际依据且未决清单为空，才声称声明范围完成。若有排除项须说明原因，不能从母清单消失。

## 适用边界

完整性只对声明语料和需求负责，不是全球穷尽。摘要可合并重复来源，但不能按共同关键词合并不同义务；尝试修复不是确认修复，人工认可与技术检查也属于不同证据。
