> These examples and illustrative results are independently authored teaching materials, not measured model results.

## Use case

Choose settings structure: grouped page A, sidebar B or item panels C. Teaching data has the same eight settings/long names. Empty isolated images hide real navigation density.

## Mechanism

Keep host header/navigation and identical read-only data on an existing page, switching structure with shareable variant parameters. Declare each structural hypothesis rather than color swaps and stub real writes. Compare identical tasks/widths/data for finding settings, returning and narrow screens, retaining links/observations. Use an explicitly marked prototype route only without a suitable host.

## Bad example

```text
Show three differently colored empty pages with different data and pick the prettiest as production implementation.
```
{: .example--bad}

## Good example

```text
Render three structures on one settings route using variant parameters, fixed eight items/long names and real surrounding navigation. Compare finding notifications and returning to overview, stubbing writes. Keep URLs/matched-width screenshots and label the structural prototype.
```
{: .example--good}

## Why the change matters

Shared host/data reduces confounding and directs comparison toward structure. Real density exposes wrapping, navigation and hierarchy absent from empty drafts.

## Observable expectation

Teaching URLs survive refresh with the correct variant/data; long names at 375 pixels do not cover controls. Record task steps/observations rather than color preference. Screenshots state which interactions actually work.

## Limits

Prototypes do not establish production quality, authentication or persistence. Real context follows authorization and effect isolation; URLs must not expose private data. Matched data improves comparability but one observation does not represent every user.
