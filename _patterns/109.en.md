> These examples and illustrative results are independently authored teaching materials, not measured model results.

## Use case

Read teaching project P9 issue I17 through an installed SaaS connector. Discover current actions/schemas and verify account/access; frozen slugs are not presumed registered capability.

## Mechanism

Bind discovery→connection→execution to one workflow/target. Inspect actual project_id/issue_id schema, effective account/connection/access and validated read inputs. Verify returned identity/completeness and report failures without invented issue prose.

## Bad example

```text
Call imagined fetchIssue, assume authentication and accept any I17 as P9; treat an active connection as permission to comment.
```
{: .example--bad}

## Good example

```text
Discover current issue-read/schema for P9/I17. Verify actual string fields, workflow/account connection and P9 access. Construct documented arguments rather than unknown slugs. Read only, validate returned target and preserve authentication/incomplete/unavailable gaps. Do not infer comment permission.
```
{: .example--good}

## Why the change matters

Action, authentication and schema address separate prerequisites. Their binding plus result identity prevents defaults/same-number records from becoming wrong evidence.

## Observable expectation

The teaching trace has discovered action/account/parameters and matching P9/I17 or explicit failure. Other-project I17 fails identity; empty data generates no fabricated description.

RUBE names are frozen instances; no live service connects.

## Limits

Active connection is not universal authorization. Provider identifiers/states change; reads grant no send/write rights. Source finance/realtime examples demonstrate structure, not current API/prices/keyless guarantees.
