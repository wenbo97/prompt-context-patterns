## 读者与完成标准

读者了解基本 AI／开发概念，希望找到一种能用于自己任务的做法。正文应让读者回答五个问题：

1. 我正在做什么任务，开始前需要哪些资料或能力？
2. 我应该依次做什么，在哪一步判断或停下？
3. 我可以如何改写指令，哪些值需要换成自己的值？
4. 我应该检查什么，什么结果说明做法没有满足要求？
5. 在哪些条件下需要调整做法，或不能据此作出结论？

方法简单时可以用短段落回答，不设字数下限。复杂方法应展开步骤、判断和失败处理，不用一句概括替代流程。篇幅增加本身不算完成。

## 七个栏目的写法

现有二级标题和锚点保持不变，顺序如下。复杂流程在对应栏目内使用步骤、加粗标签或表格展开，不另换一套顶层结构。

| 中文标题 | 英文标题 | 必须写清 | 审阅时检查 |
| --- | --- | --- | --- |
| 使用场景 | Use case | 一个具体任务、开始时已有的输入、必要前提，以及当前问题。 | 读者能判断自己的任务是否相似；需要的文件、权限或接口能力没有藏在后文。 |
| 具体做法 | Mechanism | 按执行顺序写操作、所用输入、关键判断和输出；指出缺失条件时如何处理。 | 按步骤能够执行；每一步有明确对象；机制没有只重复摘要或“为什么这样改”。 |
| 反例 | Bad example | 一条可以完整理解的失败指令，使用与改进写法相同的任务和已知事实。 | 能指出具体缺陷及其可能造成的问题；不靠删除必要输入或换任务来制造对照。 |
| 改进写法 | Good example | 同任务下可使用的完整替代指令；必要时给出最小参考材料，并解释占位符。 | 读者无需猜路径基准、字段含义、完成条件或所需资料；所有关键修改都能对应到缺陷。 |
| 为什么这样改 | Why the change matters | 将指令中的具体修改与反例缺陷联系起来，解释它怎样改变操作或判断。 | 不只重复“更清晰”“更可靠”；不把合理机制推断写成模型实测效果。 |
| 如何验证 | Observable expectation | 检查对象或记录、检查方式、通过条件及失败表现。 | 检查能发现本篇反例的具体问题；不使用“结果更好”作为唯一判据。 |
| 适用边界 | Limits | 必要前提、资料或执行成本、需要调整或停止的条件，以及检查不能证明的结论。 | 读者知道何时不能照用；不补写与本方法无关的通用警告。 |

“反例”中的失败是教学设计预期，不声称实际模型已经这样输出。“如何验证”可以给出读者应执行的检查；未实际运行的检查不写成已通过。

## 正反例与教学材料

- 先固定任务、输入与已知事实，再设计对照。修改影响方法的条件时，要在两侧同时交代。
- 反例应完整可理解，不能只有“不要这样做”的评价。改进写法应是可替换使用的指令，不能只是描述一条好指令应该包含什么。
- 示例涉及文件、数据表或接口结果时，提供完成教学任务所需的最小内容。虚构材料明确标为教学材料，不能伪造真实来源、服务响应或实测记录。
- 指令使用占位符时，紧邻说明每个占位符代表什么、由谁提供、从哪里取得。能直接给出的教学值不留给读者猜。
- 尽量集中展示导致失败的关键差异；方法确实有多个必要步骤时，分别解释这些步骤怎样修复缺陷。
- 一篇包含两种任务时，每一种任务各自形成同任务对照。P224 的 API 分页和生成续写分别比较，不能拿两种任务互相充当正反例。
- 示例继续使用 Markdown 围栏。每个反例区块的关闭围栏后保留 `{: .example--bad}`，每个改进区块保留 `{: .example--good}`；不要依赖区块恰好紧跟某个标题来标色。
- 保留页面开头的教学构造声明。需要字面显示的 Liquid 示例仍应受保护，不能在构建时执行或消失。

## 中文表达与双语一致性

先把中文任务与步骤写完整，再同步英文，最后逐篇核对以下内容：

| 核对项 | 要求 |
| --- | --- |
| 任务与前提 | 两种语言的任务、输入、权限条件和接口能力一致。 |
| 流程与判断 | 操作顺序、停止条件、既有授权处理及缺失资料处理一致。 |
| 示例与字面值 | 教学数据、路径、字段、标识符、数值和占位符对应一致；说明文字可以自然翻译。 |
| 输出与检查 | 输出对象、通过条件、失败表现及未知状态一致。 |
| 边界与证据 | 同样保留来源未说明之处、教学约定、未实测限制和适用条件。 |

中文优先使用具体动作和短句。第一次出现必要术语时，用一句话解释其用途；例如解释“游标”是服务给出的续取标记，而不是只堆叠英文名。文件名、元数据键和调用名称按其实际拼写保留。

英文应达到相同教学深度，不能只保留中文扩写前的一句概括。双语等价不要求逐字翻译或段落长度相同。

避免“赋能”“优化效果”等无法检查的表达。需要讲机制时，直接说明哪一步减少了什么猜测、保留了什么状态，或使哪个检查成为可能。

## 六篇样稿的专项要求

以下是后续正文实施与验收的检查条件，不是本轮已经执行的结果。

| 样稿 | 固定任务与写法 | 必须覆盖的正常与异常情况 |
| --- | --- | --- |
| P1：Skill 元信息 | PR 审查 Skill。两侧都有合法 frontmatter 和相同最小正文；主要差异集中在模糊描述与明确触发条件。解释 `name`、`description` 及宿主发现元信息的前提。 | 元信息解析；审查请求与实现请求的区别。实际触发检查依赖支持该格式的宿主，不把静态检查当作触发实测；任意 YAML 字段不能执行工具权限。 |
| P8：关键操作前确认授权 | 生产告警规则。明确目标、阈值、接收者和通知行为；准备禁用规则、验证、展示操作、核对授权，再决定是否启用。 | 授权先于启用；拒绝或未回答时保持禁用；既有且覆盖该操作的授权无需重复获取。只提供教学流程，不操作真实告警系统。 |
| P23：按需读取参考文件 | 根据服务 ID 分配负责人。给出最小负责人表，说明相对路径基准、读取时机、查找键和引用方式。 | 有记录时输出团队及对应记录；服务无匹配、文件不存在、文件无法读取分别报告原因；不猜负责人；说明资料版本可能过期。 |
| P224：未完成任务的续接 | 分别展开 API 分页和长文续写，各自提供正反例。服务游标原样保存；生成任务记录最后完整单元和下一单元。说明示例字段是教学约定，实际接口以其文档为准。 | 已知与未知总数；部分与完成状态；没有有效服务续接方式时的报告。生成续写从指定单元开始，不重复已完成单元；自写标签不能充当服务游标。 |
| P323：全局设计规则与页面差异 | 结账页设计规则。给出主文件、只含差异的页面文件及最终有效规则；教学约定使用字段级覆盖，页面具名字段优先，其余继承。 | 字段覆盖、未提及字段继承、无页面文件时回退主文件、缺少主文件时报告缺失。明确字段级覆盖是教学约定，上游没有完整规定合并语义。 |
| P387：按用户旅程比较同类产品 | Python SDK 上手流程。给出本产品与同类产品的虚构教学记录，列明角色、起点、结果、步骤、耗时证据类型和材料出处；由比较结果提出目标选择问题。 | 起止边界不同不做倍数排名；估算标为估算，未知保持未知；人工上手与自动执行分开；目标未选择时保留待选择状态，不替用户回答。 |

## 来源与事实边界

六篇方法已记录的冻结来源是正文核对依据。本轮规划已读取相关来源片段；后续改写不扩展上游研究，也不执行来源 Skill。

- 原文中出现过某方法，只能支持“存在这一实例”，不能据此认定最早出处。
- 本站为了让教学例子可执行而补充的路径、字段或规则，应标明为教学约定。P323 的字段级覆盖尤其需要这样处理。
- 未知总数、未知耗时、缺失资料和未获得的用户答案必须保持未知或未完成，不能为了让例子完整而编造。
- 编辑收录标准衡量内容是否具体完整，与模型成功率分开。保留现有 0–2 分制、总分至少 8 分且场景／机制／对照各 2 分的准入规则；扩写不自动提高记录中的分数。
- 如发现方法机制、来源归属或合并关系需要实质调整，单独记录问题，不混入正文润色。

## 编辑与验证流程

按已批准的续接计划，将界面与 P1、P8、P23、P224、P323、P387 的中英文样稿一起完成后审阅。每篇先核对任务与来源，再写正文，最后按七栏目和双语表自查。全部六篇完成后一次性交付样稿验收，不逐篇追加确认。

正文编辑 `_patterns/`。本批允许按内容需要完善 `_data/patterns.json` 的标题和摘要，保留身份、来源和数据结构；浏览器搜索场景从正文生成，不手写额外的场景字段，也不直接修补派生 JSON。

完成正文后执行：

1. Node 单元测试、目录与来源检查。
2. 普通生成与确定性检查；确认手写正文没有被覆盖。
3. Liquid 字面值检查、Jekyll 构建和渲染链接检查。
4. 现有 Playwright／Axe 套件，包括阶段一界面回归。
5. 检查 12 个详情页的七栏目锚点、语言切换、正反例属性及来源链接；核对搜索中的场景与正文一致。
6. 在 375／768／1280px 检查长指令、表格和代码块；查看键盘、无 JavaScript 阅读及 200% 等效重排。等效视口检查不能表述为实际操作浏览器缩放。

未修改 Patternfoo 时，其完整测试仍安排在既定最终验证阶段。内容改写优先复用现有检查，不为正文措辞建立机械匹配的测试。

## 样稿验收材料与判据

后续样稿完成后，将结果追加到本文件，包含：

- 六篇中文和英文预览入口。

- 各篇七栏目检查和双语一致性结论；明确列出未解决的问题。

验收时检查读者是否能依据给定材料执行步骤、替换自己的值，并辨认失败或未完成状态。技术检查通过不代表用户已认可中文表达与教学深度，也不替代样稿人工验收。
