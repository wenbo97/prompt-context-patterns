Exact full-content duplicates may be mapped after LF normalization. English host variants are compared through their complete canonical differences. Embedded JSON agent prompts are decoded and compared against their paired Markdown body; metadata and any changed body are still inspected. Under the user's revised relevance scope, method-bearing instructions, conditions, context pointers and essential prompt/templates/examples receive full or difference review. Domain API implementation, runtime/test/deployment scaffolding, catalog data and marketing receive explicit scoped-relevance decisions according to their actual purpose; they do not receive an equally deep upstream correctness/security/performance audit. Completed deeper findings remain as source limitations, not new work. Translations are not marked equivalent merely because headings, paths or code blocks resemble the canonical source.

The [German glossary](https://github.com/affaan-m/ECC/blob/ef648e01899ba3e8dc6371642deaaf64b4477775/docs/de-DE/GLOSSARY.md#L5-L24) and [Polish glossary](https://github.com/affaan-m/ECC/blob/ef648e01899ba3e8dc6371642deaaf64b4477775/docs/pl/GLOSSARY.md#L5-L22) explicitly define this boundary. None of these source scripts, tools, sample invocations or teaching fixtures were executed during the research.

Unchanged mechanisms map to existing `harvest-ecc.json` candidate keys; invocation, context loading, tool binding, authorization, validation and progress examples may also map to reviewed legacy IDs. An omitted constraint is a coverage finding, not automatically a new pattern. Any genuinely new variant candidate must still receive its own bilingual eight-field teaching example, scope boundaries, editorial scores and pinned source ranges. No source skill or script is executed during this review, and no external mirror is modified.

Coverage candidate links are **comparison targets**, not additional positive source citations. The per-path reason distinguishes retained and omitted mechanisms. Only the `sources` of an authored candidate are pinned positive provenance. `coverage.proof` uses the separate `comparison-context` role for exact before/after source ranges.

The eventual note will include complete per-locale semantic dispositions, source-quality limitations, newly extracted mechanisms if any, and the final zero-pending validation. Until then, use the live JSON coverage counts and pending paths as the continuation contract.
